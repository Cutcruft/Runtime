# Устройство Плагинов

## 1. Назначение

Плагин — внешний JAR-пакет, расширяющий Runtime предметными моделями, командами и UI-описаниями. Плагины находятся вне репозитория Runtime, загружаются динамически и считаются полностью доверенным кодом.

Runtime работает без плагинов. Встроенные команды `project.*` обеспечивают базовый жизненный цикл проектов.

## 2. Структура плагина

```
server-plugin/
├── pom.xml
├── config.yaml
├── src/main/kotlin/...
└── target/server-plugin.jar
```

### 2.1 config.yaml

```yaml
id: server
version: 1.0.0
apiVersion: 1
main: com.example.server.ServerPlugin

dependencies:
  - plugin: database
    version: ">=1.0 <2.0"
```

| Поле | Обязательность | Описание |
|---|---|---|
| `id` | Да | Уникальный идентификатор плагина |
| `version` | Да | Версия (semver) |
| `apiVersion` | Да | Версия Plugin API (мажорная версия `runtime-sdk`) |
| `main` | Да | Класс `Plugin` |
| `dependencies` | Нет | Зависимости от других плагинов |

### 2.2 JAR

Исполняемый код: `${id}.jar` в корне плагина, либо единственный JAR в директории плагина.

## 3. Plugin API

Плагин компилируется против артефакта `io.runtime:runtime-sdk` — отдельной библиотеки с контрактами Plugin API (без ядра Runtime). Пакеты: `runtime.domain.plugin`, `runtime.domain.command`, `runtime.domain.entity`, `runtime.domain.obj`.

### 3.1 Plugin

```kotlin
package com.example.server

import runtime.domain.plugin.Plugin
import runtime.domain.plugin.PluginContext
import runtime.domain.plugin.PluginId
import runtime.domain.plugin.PluginInfo
import runtime.domain.plugin.PluginVersion

class ServerPlugin : Plugin {
    override val info = PluginInfo(PluginId("server"), PluginVersion("1.0.0"), 1)

    override fun initialize(context: PluginContext) {
        context.registerEntity(ServerDefinition)
        context.registerCommand(CreateServerCommand())
        context.registerCommand(UpdateServerCommand())
        context.registerUi(ServersPage)
        context.registerUi(ServersNavigation)
    }
}
```

Менеджер плагина (`Plugin`) не хранит реестры. Расширения регистрируются в `initialize(context)` через `PluginContext`.

### 3.2 PluginContext

```kotlin
interface PluginContext {
    fun registerEntity(definition: EntityDefinition)
    fun registerCommand(command: Command)
    fun registerUi(ui: UIDefinition)
}
```

## 4. Модели

Модель — обычный Kotlin-`data class`. Ядро не требует аннотаций и наследования: при save/load сериализация выполняется Jackson по рефлексии, класс берётся из `EntityDefinition.modelClass`.

```kotlin
data class Server(
    val hostname: String,
    val ip: String,
    val port: Int
)
```

```kotlin
object ServerDefinition : EntityDefinition {
    override val type = EntityType("server.server")
    override val modelClass = Server::class.java
}
```

**Связи между сущностями** ядро не предоставляет. Связь описывается полем модели с `ObjectRef` — ссылкой `{entityType, objectId}` на другой объект:

```kotlin
data class Task(
    val title: String,
    val status: String,
    val board: ObjectRef? = null   // ссылка на demo.board
)
```

`ObjectRef` сериализуется ядром как обычное поле; для ссылки хватает id и типа, конкретный класс связанного объекта плагину знать не нужно (см. раздел 8).

## 5. Команды

### 5.1 Базовый класс

```kotlin
package runtime.domain.command

abstract class Command(
    val name: String,          // [a-z][a-z0-9]*
    val description: String = ""
) {
    abstract suspend fun execute(context: CommandContext, params: Any?): CommandResult
}
```

Полный идентификатор команды в реестре ядра: `<pluginId>.<name>`. Например, для плагина `server` и команды `create` — `server.create`.

### 5.2 Пример команды создания

```kotlin
class CreateServerCommand : Command("create", "Create a server") {
    override suspend fun execute(context: CommandContext, params: Any?): CommandResult {
        val p = params as? Map<*, *> ?: return CommandResult.error("Missing parameters")
        val server = Server(
            hostname = p["hostname"] as String,
            ip = p["ip"] as String,
            port = (p["port"] as Number).toInt()
        )
        // Ссылка на ObjectList проекта (без копирования)
        val list = context.objectList<Server>(EntityType("server.server"))
        val ref = list.create(server)
        return CommandResult.success(value = server, references = listOf(ref))
    }
}
```

### 5.3 Обновление / удаление

```kotlin
val list = context.objectList<Server>(EntityType("server.server"))
val current = context.getObject<Server>(EntityType("server.server"), ref.objectId)
    ?: return CommandResult.error("Server not found")
list.update(ref.objectId, current.copy(ip = "10.0.0.2"))
list.delete(ref.objectId)
```

## 6. CommandContext

| Метод | Назначение |
|---|---|
| `getObject(entityType, objectId)` | Получение объекта по типу и идентификатору |
| `objectList(entityType)` | Ссылка на `ObjectList` проекта |
| `withProjectLock {}` | Атомарное выполнение блока под блокировкой проекта |

Проект и его id командам плагина недоступны — это внутренняя информация ядра.

### Многопоточность

Команды выполняются на `Dispatchers.Default` и могут работать параллельно. `ObjectList` потокобезопасен (ReadWriteLock). Если команда выполняет несколько изменений как атомарную операцию — оберните их в `withProjectLock`:

```kotlin
class TransferCommand : Command("transfer") {
    override suspend fun execute(context: CommandContext, params: Any?): CommandResult {
        return context.withProjectLock {
            // серия согласованных изменений
            CommandResult.success()
        }
    }
}
```

## 7. Сохранение и загрузка проекта

Ядро сериализует состояние проекта в JSON (Jackson). Хранение (файл, БД, remote) — задача persistence-плагина.

Плагин-хранилище может использовать встроенные команды:

- `project.save` — возвращает `{projectId, data}` (JSON);
- `project.load` — принимает `data` и восстанавливает проект.

Напрямую `ProjectService`/`Project` плагинам недоступны — только команды `project.*`.

## 8. Зависимости плагинов

Указываются в `config.yaml`:

```yaml
dependencies:
  - plugin: demo
    version: "1.x"
```

Runtime разрешает их топологической сортировкой (`DependencyResolver`): плагин-зависимость загружается раньше. При циклической зависимости запуск отклоняется.

**ClassLoader-изоляция:** каждый плагин получает собственный `PluginClassLoader` (parent-first, родитель — ядро). Модельные классы плагинов между собой не разделяются — плагин не может импортировать классы другого плагина. Кросс-плагинный доступ работает через:

- строковые `EntityType` (`"demo.task"`), без типизации: `context.objectList<Any>(type)` / `context.getObject<Any>(type, id)`;
- сериализацию значений по рантайм-типу (например, Jackson), когда конкретный класс не нужен.

Зависимость означает совместимость с API другого плагина (его сущности зарегистрированы). Ограничение версии на данный момент хранится в дескрипторе, но не проверяется при разрешении.

Эталон кросс-плагинного плагина — `demo-storage` (см. [Демо плагин.md](Демо%20плагин.md)).

## 9. Жизненный цикл

| Состояние | Описание |
|---|---|
| DISCOVERED | Плагин найден в директории |
| LOADED | JAR загружен через `PluginClassLoader` |
| VALIDATED | Metadata и зависимости проверены |
| REGISTERED | Entities/Commands/UI зарегистрированы (`initialize`) |
| STARTED | Выполнен `start()` |
| STOPPED | Выполнен `stop()` |

Hot reload не поддерживается — изменения применяются после перезапуска Runtime.

## 10. ClassLoader

```
Runtime ClassLoader (System)
    └── PluginClassLoader (parent-first)
            └── plugin-classes
```

Parent-first: `PluginClassLoader` сначала запрашивает классы у родителя (Runtime API), затем у себя.

## 11. UI DSL

UI описывается декларативно через `UIDefinition` — интерфейс с двумя свойствами: `componentType: String` и `config: Map<String, Any>`. Плагин реализует его простым классом:

```kotlin
data class UiComponent(
    override val componentType: String,
    override val config: Map<String, Any>
) : UIDefinition
```

| componentType | Назначение |
|---|---|
| `Page` | Страница (`id`, `title`) |
| `Navigation` | Пункт навигации (`id`, `label`, `pageId`) |
| `Table` | Таблица объектов (`pageId`, `entityType`) |
| `Button` | Кнопка команды (`label`, `command`) |
| `Form` | Форма создания/редактирования |

Примеры:

```kotlin
UiComponent("Page", mapOf("id" to "servers", "title" to "Servers"))
UiComponent("Navigation", mapOf("id" to "nav-servers", "label" to "Servers", "pageId" to "servers"))
UiComponent("Table", mapOf("pageId" to "servers", "entityType" to "server.server"))
UiComponent("Button", mapOf("label" to "Create Server", "command" to "server.create"))
```

Frontend не знает реализации плагинов — только UI-метаданные из `/config`.

## 12. Пример минимального плагина

> Полный эталон (две сущности, связи, зависимости, UI) — в [Демо плагин.md](Демо%20плагин.md).

```yaml
# config.yaml
id: demo
version: 1.0.0
apiVersion: 1
main: com.example.demo.DemoPlugin
```

```kotlin
package com.example.demo

import runtime.domain.command.Command
import runtime.domain.command.CommandContext
import runtime.domain.command.CommandResult
import runtime.domain.entity.EntityDefinition
import runtime.domain.entity.EntityType
import runtime.domain.obj.ObjectId
import runtime.domain.obj.ObjectRef
import runtime.domain.plugin.Plugin
import runtime.domain.plugin.PluginContext
import runtime.domain.plugin.PluginId
import runtime.domain.plugin.PluginInfo
import runtime.domain.plugin.PluginVersion
import runtime.domain.plugin.UIDefinition
import java.util.UUID

data class Task(
    val title: String,
    val status: String,
    val board: ObjectRef? = null
)

object TaskDefinition : EntityDefinition {
    override val type = EntityType("demo.task")
    override val modelClass = Task::class.java
}

data class UiComponent(
    override val componentType: String,
    override val config: Map<String, Any>
) : UIDefinition

class DemoPlugin : Plugin() {
    override val info = PluginInfo(PluginId("demo"), PluginVersion("1.0.0"), 1)

    override fun initialize(context: PluginContext) {
        context.registerEntity(TaskDefinition)
        context.registerCommand(CreateTaskCommand())
        context.registerCommand(CompleteTaskCommand())
        context.registerUi(UiComponent("Page", mapOf("id" to "tasks", "title" to "Tasks")))
        context.registerUi(UiComponent("Navigation", mapOf("id" to "nav-tasks", "label" to "Tasks", "pageId" to "tasks")))
    }
}

class CreateTaskCommand : Command("create", "Create task") {
    override suspend fun execute(context: CommandContext, params: Any?): CommandResult {
        val p = params as? Map<*, *> ?: return CommandResult.error("Missing parameters")
        val title = p["title"] as? String ?: return CommandResult.error("Missing title")
        return context.withProjectLock {
            val task = Task(title = title, status = "open")
            val ref = context.objectList<Task>(EntityType("demo.task")).create(task)
            CommandResult.success(value = task, references = listOf(ref))
        }
    }
}

class CompleteTaskCommand : Command("complete", "Complete task") {
    override suspend fun execute(context: CommandContext, params: Any?): CommandResult {
        val p = params as? Map<*, *> ?: return CommandResult.error("Missing parameters")
        val id = ObjectId(UUID.fromString(p["id"] as String))
        return context.withProjectLock {
            val list = context.objectList<Task>(EntityType("demo.task"))
            val current = list.get(id) ?: return@withProjectLock CommandResult.error("Task not found")
            val updated = current.copy(status = "done")
            list.update(id, updated)
            CommandResult.success(value = updated, references = listOf(ObjectRef(EntityType("demo.task"), id)))
        }
    }
}
```

## 13. Сборка плагина

### 13.1 pom.xml

Плагин компилируется против `runtime-sdk` (scope `provided` — JAR плагина не включает классы SDK, они загружаются из ядра):

```xml
<project ...>
    <dependencies>
        <dependency>
            <groupId>io.runtime</groupId>
            <artifactId>runtime-sdk</artifactId>
            <version>0.1.0-SNAPSHOT</version>
            <scope>provided</scope>
        </dependency>
    </dependencies>
</project>
```

### 13.2 Сборка и размещение

```bash
mvn package
```

Результат: `target/server-plugin.jar` + `config.yaml` в корне плагина.

Размещение:

```bash
cp -r server-plugin /opt/runtime/plugins/
```

Директории плагинов указываются в `config/application.yaml`:

```yaml
server:
  host: 0.0.0.0
  port: 8080

plugins:
  directories:
    - /opt/runtime/plugins
```

В репозитории готовые цели: `make sdk` устанавливает SDK в `~/.m2`, `make plugin` собирает SDK и оба демо-плагина в `plugins/demo/` и `plugins/demo-storage/`, `make dev` запускает Runtime с ними.

### 13.3 Версионирование

- `runtime-sdk` версионируется по semver.
- `apiVersion` в `config.yaml` плагина = **мажорная** версия SDK, против которой плагин собран.
- Несовместимые изменения контрактов (удаление/изменение сигнатуры) — bump мажорной версии SDK и `apiVersion`; ядро проверяет `apiVersion` плагина при загрузке.
- Минорные и патч-версии SDK обратно совместимы в пределах одного `apiVersion`.

## 14. Публикация SDK

`mvn deploy` публикует `runtime-sdk` (+ source-jar, Dokka-документация) в удалённый репозиторий (по умолчанию настроен GitHub Packages — URL в `distributionManagement` корневого `pom.xml`). Пока репозиторий не настроен, используется локальный `~/.m2` (`make sdk`).

## 15. Ограничения

- Плагины — доверенный код (не sandboxed).
- Hot reload не поддерживается.
- Команда не вызывает другие команды.
- Плагин не хранит состояние Project (оно принадлежит ядру).
- Ядро не предоставляет связей между сущностями — связи описываются моделями плагина.
